# פרק 5: Lean 4 בידיים

בפרק הקודם ראינו שכמעט כל הצלחה של AI במתמטיקה נשענה על מוודא, ושבמקרה של הוכחות המוודא הוא בדרך כלל **Lean 4**. במעבדה שלנו Lean הוא יותר מכלי: הוא **גרעין האמון (trust kernel)**, המקום היחיד שממנו יכולה לצאת טענה ברמה L3, "מאומת מכונה". מי שרוצה להבין מה המעבדה עושה, לבקר את התוצאות שלה או לתרום לה, צריך לקרוא קוד Lean ברמה בסיסית לפחות. הפרק הזה הוא מדריך מעשי לקורא חכם שלא כתב Lean מעולם: התקנה, משפט ראשון, הטקטיקות הנפוצות, קריאת מטרות, התמצאות ב-mathlib, חיפוש למות, ולבסוף שני נושאים שבלעדיהם אי אפשר להבין את המעבדה: למה `sorry` אסור בתוצאות, ואיך ניסוח פורמלי יכול להיות שגוי גם כשהכול "עובר".

> **הערה על בדיקת הקוד.** סביבת הכתיבה של הפרק הזה לא אפשרה להוריד את Lean או את mathlib (הגישה לשרתי ההורדה נחסמה), ולכן **אף אחד מקטעי הקוד בפרק לא נבדק בקומפיילר**. כל בלוק מסומן בהתאם. הקוד מ-`lean/EshLab/Basic.lean` ומ-`lean/EshLab/Targets/` מועתק מהמאגר כפי שהוא, וגם הוא לא נבנה מחדש בזמן הכתיבה. לפני שמצטטים קטע כלשהו מהפרק בפרסום, מריצים אותו.

## מה זה Lean, בשתי פסקאות

Lean הוא שתי מערכות בגוף אחד: **שפת תכנות** פונקציונלית, ו**עוזר הוכחות (proof assistant)**. הוא מבוסס על תורת טיפוסים (dependent type theory), ובה יש רעיון אחד שכדאי להפנים מיד: **טענה היא טיפוס, והוכחה היא ערך מהטיפוס הזה.** כשכותבים `theorem t : 2 + 2 = 4 := ...`, אומרים "הנה ערך שהטיפוס שלו הוא הטענה 2+2=4". אם Lean מקבל את הערך, הטענה הוכחה.

מי שמחליט אם הערך תקין הוא ה-**kernel**: תוכנה קטנה יחסית, שנבדקה היטב, שבודקת כל צעד בהוכחה. כל השאר (הטקטיקות, האוטומציה, מודלי השפה שמציעים הוכחות) רק מייצרים מועמדים ל-kernel. זה מה שמאפשר למעבדה לסמוך על הוכחה בלי לסמוך על מי שכתב אותה, גם אם זה מודל שפה.

## התקנה

### elan, Lean ו-Lake

ההתקנה מתחילה ב-**elan**, מנהל הגרסאות של Lean (בדומה ל-rustup בעולם Rust). elan מתקין את Lean ואת **Lake**, מערכת הבנייה ומנהל החבילות, ודואג שכל פרויקט ירוץ בדיוק עם הגרסה שהוא מצהיר עליה בקובץ `lean-toolchain`.

```bash
# לא נבדק בקומפיילר (פקודות מעטפת)
curl -sSfL https://raw.githubusercontent.com/leanprover/elan/master/elan-init.sh | sh -s -- -y
source ~/.elan/env     # או לפתוח טרמינל חדש
lean --version
lake --version
```

במאגר שלנו הסקריפט `scripts/setup.sh` עושה את זה אוטומטית (שלב 2), ויודע לדלג אם elan כבר מותקן. כעורך מומלץ VS Code עם התוסף הרשמי `lean4`: הוא מציג בחלון צדדי את **מצב ההוכחה** (infoview) תוך כדי הקלדה, וזו הדרך העיקרית לעבוד עם Lean.

### פרויקט עם mathlib

**mathlib** היא ספריית המתמטיקה המשותפת של Lean, ובלעדיה כמעט אין מה לעשות. הדרך המהירה לפתוח פרויקט חדש שתלוי בה:

```bash
# לא נבדק בקומפיילר
lake new my_project math
cd my_project
lake exe cache get     # מוריד קבצים מהודרים מראש של mathlib
lake build
```

הפקודה החשובה ביותר כאן היא `lake exe cache get`. mathlib עצומה, וקומפילציה שלה מאפס לוקחת שעות. הפקודה מורידה קבצי `.olean` מהודרים מראש, וחוסכת את כל זה. אם שוכחים אותה, `lake build` יתחיל לקמפל את כל mathlib, ולרוב זה סימן שמשהו השתבש.

### הפרויקט של המעבדה

הפרויקט של המעבדה נמצא ב-`lean/` ונקרא `EshLab`. ההגדרות שלו ב-`lean/lakefile.toml`:

```toml
name = "EshLab"
defaultTargets = ["EshLab"]

[leanOptions]
autoImplicit = false
relaxedAutoImplicit = false

[[require]]
name = "mathlib"
git = "https://github.com/leanprover-community/mathlib4.git"
rev = "master"
```

שימו לב לשני דברים. הראשון, `autoImplicit = false`: נחזור אליו בסוף הפרק, כי הוא מונע סוג מסוים של ניסוח שגוי. השני, `rev = "master"`: זו הגדרה נוחה לשלב השלד, אבל היא לא רפרודוקטיבית, כי mathlib משתנה כל יום. ההערה בקובץ עצמו, וגם `lean/README.md`, אומרות במפורש שלפני שסומכים על תוצאה צריך **לנעול** את mathlib לתג או ל-commit מסוים, להעתיק את קובץ `lean-toolchain` של אותה גרסת mathlib, ולשמור את `lake-manifest.json` במאגר. כרגע `lean/lean-toolchain` מכיל את `leanprover/lean4:v4.24.0` כמחזיק מקום. ה-README מתאר את רצף הבנייה:

```bash
# לא נבדק בקומפיילר
cd lab/lean
lake update                                              # פותר את mathlib, כותב lake-manifest.json
cp .lake/packages/mathlib/lean-toolchain ./lean-toolchain  # מסנכרן גרסאות
lake exe cache get
lake build
```

לחלופין, `WITH_MATHLIB=1 bash lab/scripts/setup.sh` מריץ את `lake exe cache get && lake build` בפרויקט הזה (שלב 7 בסקריפט).

## המשפט הראשון

פותחים קובץ חדש, למשל `Scratch.lean`, וכותבים:

```lean
-- לא נבדק בקומפיילר
theorem two_plus_two : 2 + 2 = 4 := by
  rfl
```

שלושה חלקים:
- `theorem two_plus_two` הוא השם.
- אחרי הנקודתיים בא **הניסוח (statement)**, כלומר הטיפוס: `2 + 2 = 4`.
- אחרי `:=` באה **ההוכחה**. המילה `by` פותחת **מצב טקטיקות (tactic mode)**, שבו כותבים רשימת פקודות שבונות את ההוכחה צעד אחר צעד. כאן פקודה אחת מספיקה: `rfl` ("רפלקסיביות"), שאומרת "שני הצדדים שווים בהגדרה". Lean מחשב את `2 + 2`, מקבל `4`, ומסכים.

אפשר גם לכתוב הוכחה בלי טקטיקות, כ**ביטוי (term mode)**: `theorem two_plus_two : 2 + 2 = 4 := rfl`. בפועל, רוב ההוכחות במעבדה כתובות במצב טקטיקות, כי קל יותר לקרוא אותן ולתקן אותן.

כדי לראות מה Lean יודע, יש כמה פקודות שימושיות:

```lean
-- לא נבדק בקומפיילר
#check two_plus_two          -- מציג את הטיפוס: two_plus_two : 2 + 2 = 4
#check Nat.exists_infinite_primes
#eval 2 ^ 10                 -- מריץ חישוב: 1024
#print axioms two_plus_two   -- על אילו אקסיומות ההוכחה נשענת
```

## לקרוא מטרות

הכלי החשוב ביותר בעבודה עם Lean הוא חלון ה-infoview. כשהסמן נמצא בתוך הוכחה, הוא מציג את **מצב ההוכחה**: רשימת ההנחות שיש בידינו, ומתחתיהן, אחרי הסימן `⊢`, **המטרה (goal)**, כלומר מה שנשאר להוכיח. לדוגמה:

```
case succ
k : ℕ
ih : sumOdd k = k ^ 2
⊢ sumOdd (k + 1) = (k + 1) ^ 2
```

קוראים את זה כך: אנחנו בענף `succ` של הוכחה באינדוקציה. יש לנו מספר טבעי `k`, והנחת אינדוקציה בשם `ih` שאומרת ש-`sumOdd k = k ^ 2`. צריך להוכיח ש-`sumOdd (k + 1) = (k + 1) ^ 2`.

כל טקטיקה משנה את המצב: מוסיפה הנחה, מחליפה את המטרה, מפצלת אותה לכמה מטרות, או סוגרת אותה. ההוכחה גמורה כשלא נשארו מטרות, ו-Lean מציג "No goals". הדרך ללמוד Lean היא לכתוב טקטיקה אחת, להסתכל על המצב, ולהחליט על הבאה.

## עשר טקטיקות שכדאי להכיר

הטקטיקות הבאות מכסות חלק גדול מההוכחות הקטנות. בכל דוגמה ההערה מתארת את המטרה לפני ואחרי.

### intro: להכניס הנחה

כשהמטרה היא גרירה (`p → q`) או כמת כולל (`∀ x, ...`), `intro` מכניס את ההנחה או את המשתנה לרשימת ההנחות.

```lean
-- לא נבדק בקומפיילר
example (p q : Prop) : p → q → p := by
  intro hp hq     -- עכשיו hp : p, hq : q, והמטרה היא p
  exact hp
```

### exact: לסגור עם ערך מדויק

`exact e` סוגר את המטרה אם `e` הוא בדיוק הוכחה שלה. בדוגמה למעלה, `hp` הוא הוכחה של `p`.

### apply: לעבוד אחורה

`apply f` מתאים כש-`f` היא גרירה שהמסקנה שלה היא המטרה. Lean מחליף את המטרה בהנחות של `f`.

```lean
-- לא נבדק בקומפיילר
example (p q : Prop) (hpq : p → q) (hp : p) : q := by
  apply hpq       -- המטרה הופכת מ-q ל-p
  exact hp
```

### rw: לשכתב באמצעות שוויון

`rw [h]` מחליף במטרה כל מופע של אגף שמאל של `h` באגף ימין שלו. `rw [← h]` מחליף בכיוון ההפוך. אם אחרי השכתוב המטרה נהיית `a = a`, `rw` סוגר אותה בעצמו.

```lean
-- לא נבדק בקומפיילר
example (a b c : ℕ) (h1 : a = b) (h2 : b = c) : a = c := by
  rw [h1, h2]     -- a = c  →  b = c  →  c = c, ונסגר
```

### simp: לפשט

`simp` מפעיל אוסף גדול של כללי פישוט שמסומנים ב-mathlib (למשל `n + 0 = n`, `x * 1 = x`), ומנסה להביא את המטרה לצורה שסוגרת את עצמה. אפשר להוסיף לו למות: `simp [h]`. הוא חזק ונוח, אבל קשה לצפות מה בדיוק יעשה, ולכן בהוכחות ארוכות מעדיפים לפעמים `simp only [...]` עם רשימה מפורשת.

```lean
-- לא נבדק בקומפיילר
example (n : ℕ) : n + 0 = n * 1 := by
  simp
```

### induction: אינדוקציה

`induction n with` מפצל את המטרה לבסיס (`zero`) ולצעד (`succ`), ובצעד נותן הנחת אינדוקציה.

```lean
-- לא נבדק בקומפיילר
example (n : ℕ) : 0 + n = n := by
  induction n with
  | zero => rfl
  | succ k ih =>
    rw [← Nat.add_assoc, ih]   -- 0 + (k + 1)  →  0 + k + 1  →  k + 1
```

### omega: אריתמטיקה לינארית על שלמים

`omega` הוא אלגוריתם הכרעה לטענות לינאריות על מספרים טבעיים ושלמים (חיבור, חיסור, כפל בקבוע, אי-שוויונות, וגם `/` ו-`%` בקבוע). אם הטענה מהסוג הזה, הוא פשוט סוגר אותה.

```lean
-- לא נבדק בקומפיילר
example (a b : ℕ) (h1 : a < b) (h2 : b < 10) : a + 1 < 10 := by
  omega
```

### decide: לחשב את התשובה

`decide` מתאים לטענות שאפשר להכריע בחישוב סופי: השוואה של מספרים קונקרטיים, בדיקה על קבוצה סופית. ה-kernel עצמו מבצע את החישוב, ולכן התוצאה אמינה לגמרי. המחיר: זה איטי, ובמספרים גדולים זה לא יעבוד.

```lean
-- לא נבדק בקומפיילר
example : 2 ^ 10 = 1024 := by decide
example : ∀ x : Fin 5, x.val < 5 := by decide
```

לטקטיקה יש אחות מסוכנת, `native_decide`, שמקמפלת את החישוב לקוד מכונה ומריצה אותו. היא מהירה בהרבה, אבל משמעותה שסומכים על הקומפיילר ולא רק על ה-kernel, ולכן הכללים של המעבדה אוסרים אותה בהוכחות אלא אם הטענה מסומנת במפורש ככזו שסומכת על הקומפיילר (ראו בהמשך).

### norm_num: חשבון מספרי

`norm_num` (מ-mathlib) מוכיח טענות על מספרים קונקרטיים: חשבון בשברים, ראשוניות של מספרים קטנים, אי-שוויונות מספריים.

```lean
-- לא נבדק בקומפיילר
example : (3 : ℚ) / 4 + 1 / 4 = 1 := by norm_num
example : Nat.Prime 97 := by norm_num
```

### ring ושאר האוטומציה

`ring` מוכיח זהויות פולינומיות בחוגים קומוטטיביים, למשל `(a + b) ^ 2 = a ^ 2 + 2 * a * b + b ^ 2`. ראינו אותו כבר, ונפגוש אותו שוב בקובץ של המעבדה. בקטלוג הכלים (`data/tools.csv`, שורה T013) רשומים `grind`, `omega`, `decide` ו-`norm_num` כ"קו האוטומציה הראשון", לפני שפונים למוכיחי AI. זה עיקרון עבודה: קודם מנסים את האוטומציה הזולה והאמינה.

## סיור בקובץ Basic.lean של המעבדה

הקובץ `lean/EshLab/Basic.lean` נכתב בכוונה כ"משפטי חימום". לפי ההערה בראשו, יש לו שני תפקידים: לבדוק שה-toolchain וה-CI עובדים, ולשמש **דוגמת סגנון לסוכנים**: ניסוחים מפורשים, הוכחות קצרות, בלי `sorry`. הקוד שלהלן מועתק מהמאגר כפי שהוא (לא נבדק בקומפיילר בזמן כתיבת הפרק).

### סכום האי-זוגיים

```lean
-- מתוך lean/EshLab/Basic.lean (לא נבדק בקומפיילר בזמן הכתיבה)
def sumOdd : Nat → Nat
  | 0 => 0
  | n + 1 => sumOdd n + (2 * n + 1)

theorem sumOdd_eq_sq (n : Nat) : sumOdd n = n ^ 2 := by
  induction n with
  | zero => rfl
  | succ k ih =>
    show sumOdd k + (2 * k + 1) = (k + 1) ^ 2
    rw [ih]
    ring
```

ההגדרה `sumOdd` היא רקורסיה פשוטה: הסכום של אפס אי-זוגיים הוא 0, והסכום של $n+1$ אי-זוגיים הוא הסכום של $n$ הראשונים ועוד האי-זוגי ה-$(n+1)$, כלומר $2n+1$. המשפט אומר את הזהות המוכרת

$$1 + 3 + 5 + \dots + (2n-1) = n^2.$$

ההוכחה באינדוקציה. בבסיס, `sumOdd 0` הוא `0` לפי ההגדרה, ו-`0 ^ 2` מחושב ל-`0`, ולכן `rfl` מספיק. בצעד, המטרה היא `sumOdd (k + 1) = (k + 1) ^ 2`. הפקודה `show` כותבת מחדש את המטרה בצורה שבה אגף שמאל "נפתח" לפי ההגדרה: `sumOdd k + (2 * k + 1)`. Lean מקבל את זה כי שתי הצורות שוות בהגדרה. ה-`show` לא הכרחי מבחינה לוגית, אבל הוא הופך את ההוכחה לקריאה ומבטיח ש-`rw [ih]` ימצא את `sumOdd k`. אחרי השכתוב המטרה היא `k ^ 2 + (2 * k + 1) = (k + 1) ^ 2`, זהות פולינומית, ו-`ring` סוגר אותה.

### גאוס

```lean
-- מתוך lean/EshLab/Basic.lean (לא נבדק בקומפיילר בזמן הכתיבה)
def sumTo : Nat → Nat
  | 0 => 0
  | n + 1 => sumTo n + (n + 1)

theorem two_mul_sumTo (n : Nat) : 2 * sumTo n = n * (n + 1) := by
  induction n with
  | zero => rfl
  | succ k ih =>
    show 2 * (sumTo k + (k + 1)) = (k + 1) * (k + 1 + 1)
    rw [Nat.left_distrib 2, ih]
    ring
```

זו הנוסחה של גאוס, $2(0 + 1 + \dots + n) = n(n+1)$, בניסוח שנמנע מחילוק (חילוק במספרים טבעיים ב-Lean מעגל כלפי מטה, וזה מקור קלאסי לטעויות). המבנה זהה, עם צעד נוסף: `Nat.left_distrib 2` הוא חוק הפילוג $2(a+b) = 2a + 2b$, שהופך את `2 * (sumTo k + (k + 1))` ל-`2 * sumTo k + 2 * (k + 1)`. עכשיו `ih` יכול לשכתב את `2 * sumTo k`, ו-`ring` מסיים.

### אינסוף ראשוניים, בעזרת mathlib

```lean
-- מתוך lean/EshLab/Basic.lean (לא נבדק בקומפיילר בזמן הכתיבה)
theorem exists_prime_ge (n : Nat) : ∃ p, n ≤ p ∧ p.Prime :=
  Nat.exists_infinite_primes n
```

כאן אין טקטיקות בכלל: ההוכחה היא ביטוי. `Nat.exists_infinite_primes` הוא משפט ב-mathlib שאומר בדיוק את זה, ואנחנו פשוט מפעילים אותו על `n`. זו דוגמה לעיקרון "לא בונים מה שקיים": חלק גדול מהעבודה ב-Lean הוא למצוא את הלמה הנכונה ב-mathlib. בהמשך נראה איך מחפשים.

### חישוב שה-kernel בודק

```lean
-- מתוך lean/EshLab/Basic.lean (לא נבדק בקומפיילר בזמן הכתיבה)
theorem sumOdd_ten : sumOdd 10 = 100 := by decide
```

`decide` מריץ את `sumOdd 10` בתוך ה-kernel ומשווה ל-100. זה נראה טריוויאלי, אבל זה בדיוק המנגנון שבו המעבדה מתכננת לבדוק בניות קטנות: צביעה מפורשת, גרף, קונפיגורציה. בפרק 7 נראה שמטרה G050 בבנק המטרות מתכננת להשתמש ב-`decide` כדי לאמת חסם תחתון למספר Schur באמצעות צביעה מפורשת.

## איך mathlib מאורגנת

mathlib היא עץ של מאות תיקיות ואלפי קבצים, והיא מאורגנת לפי תחומים. כמה תיקיות ראשיות שכדאי להכיר:

| תיקייה | מה יש בה |
|---|---|
| `Mathlib/Logic`, `Mathlib/Order` | לוגיקה, יחסי סדר, סריגים |
| `Mathlib/Data` | מבני נתונים מתמטיים: `Nat`, `Int`, `Rat`, `Real`, `Finset`, `List`, `Fin` |
| `Mathlib/Algebra` | חבורות, חוגים, שדות, מודולים |
| `Mathlib/NumberTheory` | ראשוניים, פונקציות אריתמטיות, שדות מספרים |
| `Mathlib/Combinatorics` | גרפים פשוטים, קומבינטוריקה אדיטיבית, Ramsey בסיסי |
| `Mathlib/Analysis`, `Mathlib/Topology` | אנליזה ממשית ומרוכבת, טופולוגיה |
| `Mathlib/MeasureTheory`, `Mathlib/Probability` | מידה ואינטגרציה, הסתברות |
| `Mathlib/LinearAlgebra`, `Mathlib/RingTheory` | אלגברה לינארית, תורת חוגים |
| `Mathlib/Geometry`, `Mathlib/CategoryTheory` | גאומטריה, תורת קטגוריות |
| `Mathlib/Tactic` | הטקטיקות עצמן: `ring`, `norm_num`, `linarith` ועוד |

שמות הלמות עוקבים אחרי מוסכמה שכדאי ללמוד, כי היא הופכת ניחוש לאפשרי. שמות של משפטים כתובים ב-snake_case ומתארים את הטענה: `mul_comm` ($ab=ba$), `add_le_add`, `Nat.exists_infinite_primes`. שמות של טיפוסים ומבנים כתובים ב-UpperCamelCase: `Nat`, `Finset`, `SimpleGraph`. מרחב השמות (namespace) אומר על איזה אובייקט מדובר: `Nat.Prime` הוא ראשוניות של מספר טבעי. בקבצים שלנו כותבים `import Mathlib` כדי לייבא את הכול. זה פשוט ונוח, במחיר זמן טעינה ארוך יותר.

## איך מוצאים את הלמה הנכונה

רוב הזמן בכתיבת Lean לא מושקע בהיגיון, אלא בשאלה "איך קוראים ב-mathlib למשפט שאני צריך?". יש שלושה כלים עיקריים, וכולם מופיעים ב-Starter Stack של המעבדה (פרק 8).

**exact? ו-apply?** הם טקטיקות שמחפשות בעצמן. כותבים `exact?` במקום ההוכחה, ו-Lean סורק את הלמות הזמינות ומציע שורה שסוגרת את המטרה, למשל `Try this: exact Nat.exists_infinite_primes n`. `apply?` מציע למות שהמסקנה שלהן מתאימה למטרה, גם אם נשארות הנחות להוכיח. `rw?` מציע שכתובים אפשריים. אלה הכלים הראשונים לנסות, והם גם רשומים כחלק מארגז הכלים של ה-lean-agent ב-`orchestrator/agents.py`.

```lean
-- לא נבדק בקומפיילר
example (n : ℕ) : ∃ p, n ≤ p ∧ p.Prime := by
  exact?      -- יציע: exact Nat.exists_infinite_primes n
```

**Loogle** הוא מנוע חיפוש לפי **צורה**. מחפשים לפי שמות קבועים, לפי תבנית של ביטוי, או לפי מחרוזת בשם. לדוגמה, השאילתה `_ * (_ + _) = _ * _ + _ * _` מחזירה את חוקי הפילוג, והשאילתה `Nat.Prime, "infinite"` מחזירה למות שמזכירות ראשוניים ושבשמן מופיעה המילה infinite. Loogle מתאים כשיודעים בדיוק איך הטענה אמורה להיראות.

**LeanSearch** הוא מנוע חיפוש בשפה טבעית: כותבים "there are infinitely many primes" ומקבלים רשימת למות מועמדות. הוא מתאים כשיודעים מה רוצים להגיד, אבל לא איך mathlib מנסחת את זה. ל-LeanSearch יש חלופה בשם Moogle (T017 בקטלוג).

סדר עבודה מומלץ: קודם `exact?`, אחר כך LeanSearch אם אין מושג איך הדבר נקרא, ו-Loogle כשיש תבנית ברורה.

## sorry: ההבטחה שלא קוימה

כשכותבים הוכחה ארוכה, נוח לדחות חלקים ממנה. Lean מאפשר זאת עם המילה `sorry`:

```lean
-- לא נבדק בקומפיילר
theorem hard (n : ℕ) : n * n ≥ n := by
  sorry
```

`sorry` אומר ל-Lean "תניח שזה הוכח". הקובץ יתקמפל, עם אזהרה (`declaration uses 'sorry'`), וכל מה שמשתמש ב-`hard` ייראה תקין. זה כלי לגיטימי בזמן הפיתוח, כמו פיגום בבניין, וזה חלק מתהליך ה-blueprint: כותבים את השלד עם `sorry` במקומות הפתוחים, וממלאים אותם בהדרגה.

אבל בתוצאה סופית `sorry` הוא שקר. משפט שמשתמש ב-`sorry` לא הוכח. ומאחר שהאזהרה היא רק אזהרה ולא שגיאה, קל מאוד לפספס אותה, במיוחד כשמודל שפה כותב אלפי שורות. לכן המעבדה קובעת כללי קבלה מפורשים להוכחה ברמה L3, שמופיעים ב-`lean/README.md`:

1. `lake build` מצליח על checkout נקי, עם ה-manifest הנעול.
2. בקובץ ההוכחה אין `sorry`, `admit`, `axiom`, `native_decide`, `implemented_by` או `@[extern]`. (`native_decide` מותר רק אם הטענה מסומנת במפורש ככזו שסומכת על הקומפיילר.)
3. `#print axioms EshLab.<theorem>` מציג לכל היותר את `propext`, `Classical.choice` ו-`Quot.sound`, שלוש האקסיומות הסטנדרטיות של Lean ו-mathlib.
4. ניסוח המשפט **זהה תחבירית** ליעד שבני אדם בדקו בתיקייה `EshLab/Targets/`. קובץ ההוכחה צריך לייבא את היעד ולהוכיח את `EshLab.Targets.<Name>` עצמו, ולא עותק שנוסח מחדש.
5. כל קובץ יעד כולל דוגמאות (`example`) שבודקות את הקידוד על מקרים קטנים.

הכלל השלישי הוא הרשת הבטוחה: גם אם `sorry` הוסתר איפשהו בשרשרת התלויות, הוא יופיע בפלט של `#print axioms` כ-`sorryAx`. גם `axiom` חדש שמישהו הוסיף, וגם השימוש ב-`native_decide`, יופיעו שם. אם הפלט נקי, ה-kernel באמת בדק הכול.

```lean
-- לא נבדק בקומפיילר; הפלט המדויק עשוי להשתנות בין גרסאות
#print axioms EshLab.exists_prime_ge
-- 'EshLab.exists_prime_ge' depends on axioms: [propext, Classical.choice, Quot.sound]
#print axioms hard
-- 'hard' depends on axioms: [sorryAx]
```

הכלל הרביעי מטפל בבעיה אחרת, עמוקה יותר, שאליה מוקדש הסעיף הבא.

## כשהניסוח עצמו שגוי

כל מה ש-Lean מבטיח הוא שההוכחה נכונה **ביחס לניסוח**. אם הניסוח לא אומר את מה שהתכוונו, ההוכחה חסרת ערך. גרוע מזה, היא מזיקה, כי היא נראית מאומתת. `docs/architecture.md` קורא לזה "אופן הכישלון מס' 1", וראינו בפרק 4 שזה קרה בפועל בפרויקט Strong PNT. הנה כמה דרכים שבהן זה קורה, מהמקרה הגס ועד העדין.

### דוגמה ראשונה: שוכחים תנאי

ככה מנוסחת השערת קולץ במעבדה, ב-`lean/EshLab/Targets/Collatz.lean`:

```lean
-- מתוך lean/EshLab/Targets/Collatz.lean (לא נבדק בקומפיילר בזמן הכתיבה)
def collatzStep (n : ℕ) : ℕ :=
  if n % 2 = 0 then n / 2 else 3 * n + 1

def CollatzConjecture : Prop :=
  ∀ n : ℕ, 0 < n → ∃ k : ℕ, collatzStep^[k] n = 1
```

`collatzStep^[k] n` פירושו "להפעיל את `collatzStep` על `n` בדיוק `k` פעמים". ההשערה: כל מספר חיובי מגיע בסופו של דבר ל-1.

עכשיו נניח שמישהו (אדם או מודל) שכח את התנאי `0 < n`:

```lean
-- לא נבדק בקומפיילר — ניסוח שגוי בכוונה
def CollatzWrong : Prop :=
  ∀ n : ℕ, ∃ k : ℕ, collatzStep^[k] n = 1
```

הניסוח הזה **שקרי**, ומסיבה טריוויאלית: 0 זוגי, ו-`collatzStep 0 = 0 / 2 = 0`. האפס תקוע לנצח ולא מגיע ל-1. מודל שמתבקש "להוכיח או להפריך" את `CollatzWrong` יפריך אותו בהצלחה בשתי שורות, וכותרת כמו "AI הפריך את השערת קולץ!" תהיה במרחק ציוץ אחד. זו לא תהיה הפרכה של שום דבר.

### דוגמה שנייה: ניסוח חלש מדי

השערת הראשוניים התאומים אומרת שיש **אינסוף** זוגות ראשוניים $p, p+2$. הנה ניסוח שנראה סביר במבט חטוף:

```lean
-- לא נבדק בקומפיילר — ניסוח שגוי בכוונה
def TwinPrimesWrong : Prop :=
  ∃ p : ℕ, p.Prime ∧ (p + 2).Prime

theorem twinPrimesWrong_proof : TwinPrimesWrong :=
  ⟨3, by norm_num, by norm_num⟩
```

הניסוח אומר רק ש**קיים** זוג תאומים אחד, וזה נכון: 3 ו-5. ההוכחה עוברת, `#print axioms` נקי, וזה משפט "מאומת ב-Lean" שאין לו שום קשר להשערה. הניסוח הנכון צריך לומר שמעל כל חסם יש זוג:

```lean
-- לא נבדק בקומפיילר
def TwinPrimeConjecture : Prop :=
  ∀ N : ℕ, ∃ p : ℕ, N ≤ p ∧ p.Prime ∧ (p + 2).Prime
```

שימו לב שזה בדיוק המבנה של `exists_prime_ge` שראינו קודם, ולא במקרה: "אינסוף" מנוסח כ"לכל N יש אחד מעל N".

### דוגמה שלישית: מלכודות של מספרים טבעיים

ב-Lean, חיסור במספרים טבעיים נקטע באפס (`3 - 5 = 0`), וחילוק מעגל כלפי מטה (`7 / 2 = 3`), כולל `n / 0 = 0`. הבחירות האלה הגיוניות מבחינה טכנית, אבל הן מייצרות טענות שנראות נכונות ואינן:

```lean
-- לא נבדק בקומפיילר
example : ∀ n : ℕ, (n - 1) + 1 = n := by
  sorry   -- שקרי! עבור n = 0: (0 - 1) + 1 = 0 + 1 = 1 ≠ 0
```

ניסוח השערה שכולל ביטוי כמו `n - 1` או `a / b` על מספרים טבעיים, בלי תנאים מתאימים, עלול לשנות את המשמעות לגמרי. לכן `two_mul_sumTo` שראינו מנוסח עם כפל ב-2 ולא עם חילוק ב-2.

### דוגמה רביעית: משתנה שנולד מטעות הקלדה

כאן נכנסת ההגדרה `autoImplicit = false` מה-lakefile. כשהאפשרות הזו פעילה (וזו ברירת המחדל של Lean עצמו), Lean מתייחס לשם לא מוכר **בכותרת** של הצהרה, כלומר בניסוח של משפט, כמשתנה חדש שנוסף אוטומטית כפרמטר מובלע. נניח שכותבים משפט על השערת גולדבך עם טעות הקלדה, `m` במקום `n`:

```lean
-- לא נבדק בקומפיילר — עם autoImplicit פעיל, זה עלול להתקבל ולשנות משמעות
theorem goldbach_attempt :
    ∀ n : ℕ, 2 < n → Even n → ∃ p q : ℕ, p.Prime ∧ q.Prime ∧ p + q = m := by
  sorry
```

עם `autoImplicit` פעיל, Lean עלול להוסיף בשקט פרמטר מובלע `{m}` ולקבל את הניסוח. עכשיו זו טענה אחרת לגמרי, על מספר `m` קבוע, שהיא שקרית לרוב ערכי `m` ולא קשורה לגולדבך. כש-`autoImplicit = false`, Lean מסרב: "unknown identifier 'm'". זו שורת הגדרה אחת שמונעת קטגוריה שלמה של שגיאות, ולכן היא מופיעה בפרויקט של המעבדה.

### איך המעבדה מתגוננת

ההגנה היא שילוב של כמה שכבות, וכולן מופיעות בקבצים:

- **ביקורת אנושית לפני כל מאמץ הוכחה.** כל יעד חדש בתיקייה `Targets/` חייב אישור של אדם. ההערה בראש `Collatz.lean` אומרת במפורש `reviewed-by-human = false`: הניסוח עוד לא אושר.
- **דוגמאות שפיות (sanity examples).** כל קובץ יעד כולל `example`-ים שבודקים את הקידוד על מקרים קטנים. ב-`Collatz.lean`:

```lean
-- מתוך lean/EshLab/Targets/Collatz.lean (לא נבדק בקומפיילר בזמן הכתיבה)
example : collatzStep^[7] 3 = 1 := by decide   -- 3 → 10 → 5 → 16 → 8 → 4 → 2 → 1
example : collatzStep 1 = 4 := by decide       -- מוסכמת המעגל הטריוויאלי
```

  ובקובץ `Goldbach.lean`:

```lean
-- מתוך lean/EshLab/Targets/Goldbach.lean (לא נבדק בקומפיילר בזמן הכתיבה)
def GoldbachConjecture : Prop :=
  ∀ n : ℕ, 2 < n → Even n → ∃ p q : ℕ, p.Prime ∧ q.Prime ∧ p + q = n

example : ∃ p q : ℕ, p.Prime ∧ q.Prime ∧ p + q = 10 :=
  ⟨3, 7, by norm_num, by norm_num, rfl⟩
```

  המפרט של ה-lean-agent (`agents/lean-agent.md`) דורש דוגמאות גם למקרים **נכונים** וגם למקרים **שאמורים להיכשל**. דוגמה כמו `example : collatzStep 0 = 0 := by decide` הייתה מראה מיד למה התנאי `0 < n` הכרחי. בקבצים הנוכחיים יש רק דוגמאות חיוביות, וזה פער שכדאי לסגור.
- **תרגום חזרה לשפה טבעית.** כל יעד מלווה בתיאור מילולי (docstring) של מה שהוא אומר, כדי שבודק אנושי יוכל להשוות למקור.
- **הוכחה של היעד עצמו.** כלל הקבלה הרביעי דורש להוכיח את `EshLab.Targets.<Name>` שנבדק, ולא "עותק" שנוסח מחדש בקובץ ההוכחה. כך אי אפשר להחליף בשקט ניסוח קשה בניסוח קל.
- **השוואה לניסוחים קיימים.** כשיש ניסוח ב-mathlib או ב-Formal Conjectures, משווים אליו. זה בדיוק מה שנעשה בפרויקט FLT של 2026.

## בקצרה

- ב-Lean טענה היא טיפוס והוכחה היא ערך. ה-kernel הקטן בודק כל הוכחה, ולכן אפשר לסמוך על התוצאה בלי לסמוך על הכותב.
- ההתקנה: elan, ואחריו Lake, ובפרויקט עם mathlib חובה להריץ `lake exe cache get`. לתוצאות רפרודוקטיביות נועלים את גרסת mathlib.
- עשר טקטיקות (`intro`, `apply`, `exact`, `rw`, `simp`, `induction`, `omega`, `decide`, `norm_num`, `ring`) מכסות חלק גדול מההוכחות הקטנות. קוראים את המטרה אחרי כל צעד.
- חיפוש למות: `exact?` קודם, LeanSearch לשפה טבעית, Loogle לתבניות.
- `sorry` אסור בתוצאות. `#print axioms` חושף אותו, וגם `axiom` חדש ו-`native_decide`.
